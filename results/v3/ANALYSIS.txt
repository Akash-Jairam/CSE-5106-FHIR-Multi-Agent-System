DESIGN AND COMPARISON METHODS


ARCHITECTURE UNDER EVALUATION

V3 is the question-contract architecture, recorded as query-contract-v3.2-static-audit. A question-only contract stage has no access to the solver answer, source records or gold answer. A continuous solver retrieves and computes against FHIR data with an execution ledger and source validation. A static program audit checks the contract, executed code and bounded sources without receiving a rendered candidate answer. Supported host repair is narrowly constrained; the design does not run a second full solve or vote.

Recorded phase ceilings are 10,000 contract tokens, 175,000 solver tokens and 15,000 audit tokens, within an aggregate 200,000-token and 30-executed-tool budget. The solver has at most 20 model calls. The Single Agent is the contemporaneous implementation control; an earlier paper score would not measure this model, substrate, scorer, cache behavior and question cohort together.


FROZEN EXECUTION AND SCORING

The recorded Azure deployment is gpt-6-luna, reasoning none, with a maximum completion limit of 16,384 tokens, a 32,000-token estimated-input guard and enabled prompt caching. Full runs use two workers. The unchanged typed-answer scorer determines correctness from saved final answers and reference types. No model judge or additional inference is used for consolidation.

Full runs select the first accepted runtime-clean task outcome by the frozen collection policy. Only those selected task measurements enter the design totals. Development retains its original scheduled first-attempt scores. Unknown measurement values remain null. Missing fields are not converted to free usage or zero time.


COHORT AND UNCERTAINTY

The primary comparison joins question IDs and verifies patient IDs, giving 2,929 matched pairs and 94 patients. Patient-cluster percentile intervals resample patients 10,000 times with seed 5106, retain their questions and estimate the question-weighted mean. Pairing is preserved in differences. Intervals describe this cohort and recorded run, not repeated deployments or random model seeds.

The dataset informed development. All 300 fresh development question IDs also occur in the matched full cohort. The original split labels do not capture later development exposure; they must not be called an untouched holdout. See the exposure discussion on page 8.

Draft arithmetic reconciles within its actual scope. For Single Agent, 2,220 + 96 − 15 = 2,301 final-correct draft-present questions; 42 additional correct outputs have no saved draft. V3 has 2,135 + 171 − 56 = 2,250, plus five correct outputs without drafts. This prevents treating absent drafts as incorrect drafts or comparing stage totals to incompatible final denominators.

V3 improves more wrong drafts in absolute count, but it starts with fewer correct saved drafts and also loses more correct drafts. Net draft-present gains are +81 for Single Agent and +115 for V3. These counts are compatible with V3 having lower final accuracy and cannot be summarized simply as a successful revision rate.


SOURCE AND AUDIT BEHAVIOR

V3 records 2,640 releases under source_valid_primary_preserved and 289 under primary_failed_execution_or_source_contract. Its 351 solver source revisions and 299 answer changes describe different events and need not be equal. The matched full mechanism export records no targeted revisions or targeted wrong-primary recoveries. Together with development’s zero material audit repairs, this provides little observed evidence that the static audit supplies the intended answer-level gain.

Matched V3 evidence counts total 19,297, with 19,252 marked valid by recorded local checks. Evidence validation is unavailable for Single Agent and must not be filled with zero or compared as an accuracy score. Local source validity does not establish temporal interpretation, clinical meaning or final-answer correctness.

The baseline records 176 budget-stop flags and V3 zero. A flag is an implementation diagnostic, not a substitute for scoring the saved answer. Mechanism fields, source checks, limitations and evidence precision/recall have different missingness and denominators; their full tables preserve that information.

This handoff does not make a heldout-performance claim or construct a new confirmatory subgroup from the remaining patient.


WHAT THE EXPERIMENT ESTABLISHES

For this frozen V3 architecture and these recorded runs on the released benchmark, V3 reduces measured token and tool usage. On the available matched full cohort it has lower typed accuracy, greater per-task latency and greater cost under the recorded cache mix than the contemporaneous Single Agent control. The accuracy interval is conditional on patient sampling from this benchmark; it does not account for design selection on reused data.

A controlled causal claim about multi-agent architecture alone would require tighter isolation. Execution dates and cache states differ, the development and full code have a documented host-loop bound difference, and the cohort informed refinement. The no-cache price calculation demonstrates accounting sensitivity without simulating a new service configuration.


WHAT SHOULD TRAVEL WITH A MIDTERM FIGURE

Any accuracy figure should state the question denominator, 94-patient clustering for the full comparison, reused development data and paired interval method. Any efficiency figure should name its metric: selected task seconds, measured tokens or estimated USD. Cost figures should state the rates and the cache assumption. Keep the 300-question checkpoint separate from the full common-cohort comparison.

Do not replace typed accuracy with conditional accuracy among nonempty outputs; do not add token counts to proxy dollars; do not treat task-time sums as wall-clock run duration; and do not infer independent evidence validation where it was not recorded. These distinctions affect interpretation directly.

METRIC DICTIONARY

question_id is the join key and must be imported as text. Patient IDs define bootstrap clusters. correct is the frozen typed final-answer score. latency_seconds is selected task elapsed time. prompt_tokens includes cached_prompt_tokens; completion_tokens is output usage; total_tokens is prompt plus completion. estimated_cost_usd is the frozen-rate calculation. reported_cost_usd is unavailable provider dollar reporting, not the proxy estimate.

llm_calls and executed-tool counts measure different operations. evidence_count counts recorded evidence entries, while evidence_valid, precision and recall require recorded validation and can be missing. Draft/final transitions apply only where a draft exists. Empty/no-value, limitation and budget-stop flags retain their recorded meanings; none substitutes for typed correctness.


OFFLINE REPRODUCTION

Start from a checkout of results/v3-ful-run. Read METHODS.txt and RUN_REGISTRY.json, then work from the numeric files before restoring the much larger raw material. All commands below are local and require no model credentials.


VERIFY THE PACKAGE

1. Verify PACKAGE_MANIFEST.json and per-archive checksums. Numeric tables work without raw restoration. Blank CSV cells and JSON null mean unavailable. Baseline validation binds matched IDs, source pins, first-clean selection and arithmetic.

2. Follow full_v3/RECONSTRUCTION.txt, full_single_agent/raw/RECONSTRUCTION.txt and development/raw/README.txt. Development ZIP parts reconstruct exactly. Full-arm XZ envelopes preserve parsed canonical rows and decompressed audit text; original whitespace and gzip headers are not recreated. Standard Python JSON and LZMA libraries suffice.


READ ONE RAW QUESTION

Use the question index to find the patient chunk and line for a question ID. Each decompressed JSONL envelope has canonical and audit_json fields. canonical retains the original parsed result record; JSON-decode audit_json to inspect its saved trace and resources. The index binds row semantics, original audit payload hashes, question ownership and source ordering. This lets a reviewer inspect a discordant pair without reconstructing the whole corpus.


VERIFY OR RECONSTRUCT V3

From the repository root, run the following with Python 3.10 or newer. Verification streams every chunk and checks hashes and ownership. Reconstruction requires a new output directory outside the archive and sufficient free disk space; it writes the canonical array and fresh gzip containers with the original audit payload bytes.

python3 results/v3/full_v3/archive_tools.py verify --archive results/v3/full_v3/data_archive

python3 results/v3/full_v3/archive_tools.py reconstruct --archive results/v3/full_v3/data_archive --output /tmp/v3-restored-results

The baseline archive uses the same envelope schema. Its own reconstruction guide gives the corresponding utility and archive-directory arguments. Development uses ordered ZIP parts; its guide supplies the exact concatenation order and original SHA256.

3. Run reproduce/build_analysis.py with Python and python-docx to rebuild this handoff from saved summaries. No provider request is made. Frozen scorer and analysis sources remain pinned in Git; derived extraction sources and hashes accompany the numerical packages.

4. Use matched 2,929-question files for comparisons, the complete V3 package for the 2,931-question arm result and development files for the reused checkpoint. Full comparison paired JSON files use Single Agent minus V3; development paired tables and this handoff use V3 minus Single Agent.
