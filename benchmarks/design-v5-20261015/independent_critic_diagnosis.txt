# Completed V5 critic diagnosis

The zero-repair result is primarily a failure to produce actionable alternative answers, with additional protocol friction. It is not evidence that a final source-check gate rejected a batch of correct repairs: only one PATCH was ever proposed, its execution reproduced an already-correct answer/evidence/ID set exactly, and no critic candidate reached a source check. No concrete host implementation defect was found in these trajectories.

This is post-terminal analysis of the exposed fixed300 only. The externally pinned completion report is PASS for all600 audits; official results are Single237 / Team225. Frozen critic source is e66f7b3af92a63fd80c92f00a4bae357dc01cdf5b1d11c2f5d3ef51f3ddb42c7. The original source ZIP and six relevant current/archived public source files were checked against the frozen manifest. All300 Team gzip payloads were independently checked for compressed SHA, content SHA and owner before inspection; all334 model replies and97 charged tools reconcile with the completion guard. Scoring annotations use the unchanged frozen scorer with the exact fixed300 templates and match the formal helper on all282 critic-eligible rows. No protected confirmation QA, SQL, new model calls, retrieval or inference-source edits were used.

All282 packets fit intact: first-prompt tokens min2052, median3267.5, max4580, below5500. There were no critic accounting/provider losses, cap violations, hidden/unrecorded critic calls, or critic-stage credit losses. Reported first completions ranged31–869 tokens and second completions44–876, so observed failures are not explained by reaching the1800/4000 completion caps.

Engineering packet fit is different from semantic information coverage. The first packet contains exact original context, executable final code, ledger/completeness, hashes and one sample record per resource kind. It does **not** contain the actual computed primary answer/evidence or its selected-record trace. The critic can inspect the full frozen workspace once, but must first formulate a concrete discrepancy from that sparse view. This creates a substantial information/admission burden. In the129 final UNKNOWN reasons, a nonexclusive text census finds67 mentions of preview/visibility limits and80 of missing scope/completeness/establishment; these are overlapping markers, not independently adjudicated causal categories. Twenty-four packets have empty retrieval ledgers/completeness;126 have no explicit current-time value. Those absences do not themselves prove the primary wrong.

## What the host rejected, and what that means

The30 unusable probes are real interface friction. Fifteen produce at least one observation value larger than1024 JSON characters; one also duplicates an observation name. The12 answer-schema rejects include8 empty fact lists,3 lists exceeding16 facts, and one other case with no observations (conditions can overlap). Requiring a positive immutable fact deliberately excludes pure absence/context-only witnesses. That restriction is broader than malformed JSON, and can suppress a relevant inspection even when its summary is informative.

The three fact-validation failures are consistent with the declared contract: two cite absent fields as if they were explicit nulls; another reconstructs a `code` object with an extra `text:null` member that the immutable source does not contain. The eight anchor failures divide into three exact quotes in the wrong original channel and five quotes absent from original question/assumptions, often taken from shared system guidance. These are model/protocol provenance failures, not evidence of the host misreading a valid original anchor.

There is no observed rejected **answer-changing PATCH** that can be called a correct missed repair. Some rejected *inspections* have relevant hypotheses, but no validated alternative answer follows in the saved trajectory. The distinction matters: relaxing their formatting gates changes which counterfactual conversation could happen; it does not turn their current observations into completed repairs.

## Modest comparison with the contemporary Single policy

V5 preserves a **V3 LedgerSolver** primary, not the exact fresh SingleAgent policy. They share the Single system/semantic guidance and core computation/source checking, but differ before the critic: LedgerSolver has175k/27 (25 model-requested tools plus two host checks),20 real model calls/22 host slots, per-call remaining-budget/finalize guidance, mandatory explicit final execution from the first turn, early host transition once an executed candidate is ready, and scoped/deferred retrieval bookkeeping with unresolved-scope vetoes. Fresh Single has200k/30,30 iterations, a later model continuation after a tool batch, and a prose-final fallback until explicit-final mode has been required. V5 additionally gates the returned primary on explicit artifact/source/scope conditions. These differences are plausible contributors to divergent primaries and withheld answers, but this paired run does not isolate their causal contributions. The critic itself changes neither accuracy nor releases in this completed run.

The broad lesson is to test a mechanism that can obtain and compare substantive candidate behavior under matched resources, rather than infer that a stronger final acceptance rule or a larger JSON tolerance will solve the semantic problem. Future work still needs a frozen development experiment and untouched question-disjoint confirmation; this analysis provides no new-patient/model/task evidence.
