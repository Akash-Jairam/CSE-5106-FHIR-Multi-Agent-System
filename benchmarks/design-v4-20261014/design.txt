Motivation and distinct hypotheses
DIN-SQL's author driver feeds schema links and predicted subquestions into SQL generation; MAC-SQL retains question/schema/evidence while debugging execution. A direct FHIR planner (SaludAI) injects catalog planning into an existing tool loop. We transfer a question-only advisory handoff rather than their benchmark examples, gold schema, annotation hints, empty-result-as-error, permanent tool hiding, or incomplete-pagination assumptions.
This bundles three changes relative to V3.2: plan advice visible to the solver, removal of the mandatory late static audit/targeted repair, and more solver allocation. A future aggregate gain cannot be assigned solely to advisory planning. Fewer required model phases may affect provider reliability independently of semantic correctness. Sources do not establish equal-budget FHIR improvement.

Protocol
Same configured gpt-6-luna; aggregate 200,000 input/output tokens and 30 executed tools.
Planner: 10,000 total tokens, 0 tools, one model pass. Original question/context plus unchanged shared semantic guide only; no draft, Python program, packet, patient resources, selected IDs or gold fields.
Solver: 190,000 total tokens, 30 tools comprising 28 model-requested tools and 2 reserved automatic source checks; at most 20 actual model calls. Every original retrieval/code/check tool remains available. The unchanged V3 LedgerSolver consumes the first valid explicit final at the full tool-batch boundary, checks original sources, and permits one existing source-feedback correction. No model audit, whole-answer recomputation, vote, host semantic patch or final synthesis is required.
Global and local caps both apply; unused planner allocation does not enlarge solver's 190k local ceiling. The existing parent model/accountant and PhaseHost policy cap completions before transport. Unknown provider usage and reported cap overshoot remain fatal. Local planner refusal, format or tool-request failures, and failures with verified usage, produce ignored advice and preserved diagnostics, then let the solver proceed under its remaining caps. Provider failures with unknown usage terminate the attempt before any solver call; absent usage is never treated as known zero.

Plan interface and visibility
One finite JSON object with status READY/UNKNOWN, at most 16 steps, and at most 16 unknowns. A step contains unique ID, one declared operator, references to earlier IDs, an exact question quote, supplied span, and concise requirement/tentative mapping. Every quoted substring must occur uniquely in the original question; host derives actual [start,end) and records supplied span and normalization. A missing quote or more than one possible occurrence of that quote in the question, including overlapping repetitions, ignores the whole plan. Different steps may have distinct uniquely anchored quotes whose spans overlap. Forward/cyclic dependencies, unexpected top-level/step fields, malformed/unbounded text or UNKNOWN status also ignore the whole plan. There is no partial guessed plan.
Question provenance is not semantic truth. Requirements are advice, not deterministic constraints. The planner cannot change tools, retrieval filters, fields, joins, null policies or release gates in host code. Solver system context explicitly keeps original question/shared conventions authoritative and permits rejected/unsupported advice. The original question/context and packet still enter the unchanged SingleAgent trajectory. Freeze/hash validated advice before the first real solver call, retain raw role trace and validated/ignored plan diagnostics. No per-question known outcome routing or gold answers/SQL/template IDs are supplied.

Clinical meaning and remaining risks
A useful plan separates each operand's population/filter/window/order/selection from final projection, records requested units/fields and event versus value multiplicity, and keeps missing population, selected missing value and incomplete retrieval distinct. Repeat measurements remain distinct unless asked otherwise. Numeric totals, rate and dose are different concepts; cite exact source values even when a computed answer transforms units.
Neither CQL conventions nor catalog hints override benchmark/question semantics. CQL Count(empty)=0 differs from Sum/Avg(empty)=null, and query return may deduplicate by default; importing those defaults blindly is unsafe. Date precision/timezone semantics and Observation clinical time versus issued version time need explicit interpretation. Existing shared guidance and source checks remain unchanged.
The solver is conditioned on the plan, so it is not independent of the planner's interpretation. A wrong but textually anchored plan can anchor a wrong executed answer; no late intent audit attempts to repair it. Source validation demonstrates retrieved fields/ownership/time scope, not global correctness of question interpretation. The conservative future-only Medication linkage abstention and first-final lifecycle tradeoff inherited from V3 remain.

Successful release has final_check_issues=[]; failure releases null with actual source/execution issues. Plan errors cannot manufacture a release.
