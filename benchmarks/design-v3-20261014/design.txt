Design V3: blind question contract, integrated solver, static program audit
Substantial fixed 300-question comparison, 14 October 2026

Frozen acceptance criterion

The ordinary team must exceed both archived single 223/300 (74.3%) and the
completed refreshed single 231/300 (77.0%) with the unchanged typed scorer.
All scheduled first attempts remain in the denominator, including terminal
errors. No failed question will be retried to replace its result. No accuracy
result for this substantial V3 design is known when this record is frozen.

Run one fresh 300-question ordinary_multi_agent arm using multi_agent_v3, with

reasoning_effort none, 200,000 aggregate tokens and 30 aggregate logical tools.
The exact existing manifests/split.json held_out cohort has 300 question IDs,
58 observed patients, 92 lookup/counting, 159 temporal and 49 aggregation.
Patient IDs/current-time assumptions and starting packets remain gold-free.

Reuse the completed refreshed single control from the V2 substantial record.
Do not rewrite its source or run identity. Its shared agent/prompt/tool/scorer
code is unchanged; the combined operational helper changes affect output
transport only, with AST and inline/gzip parity evidence in the protocol audit.
The team-specific dispatcher, strict final boundary, budget signals, blind
contract and local audit are the treatment. This is a system-design comparison,
not a causal ablation of context isolation or role count alone.

The frozen V2 team result is 198/300, with 34 correct drafts discarded and 32
budget stops. This motivates preserving the integrated solving trajectory
and replacing unproductive verification vetoes with actionable local checks.
The detailed protocol, source-visible state, exact phase caps, supported repairs,
source-completeness rules and conservative limitations follow below.

Protocol caps: contract 10k tokens/0 tools; solver 175k/27 (25 model-requested
plus two reserved source checks); static audit 15k/0; targeted execution 0/3.
Exactly one static audit completion; no inspection probes, whole second solve
or final synthesis model call. Unsupported/UNKNOWN auxiliary findings preserve
a source-valid primary. Only a supported unique expression change with actual
source witnesses, changed contributors, successful replay and source checks
can replace it. No stronger model, question-ID routing, gold-answer retrieval,
best-of-N selection, or larger aggregate ceiling is used.

Source and evidence retention

The source archive and hashes are frozen before inference. Complete returned
traces, raw workspace and revision messages are losslessly externalized inside
workers before IPC; owner/path/hash checked gzip artifacts remain with the raw
output. Answers/evidence/usage/revision summaries stay inline. This operational
change improves memory/provenance and is not credited as an accuracy mechanism.
If a question fails before returning a workspace, storage cannot reconstruct it.
Credential-free adapter source/binding hashes are recorded separately.

Small development checks are not formal experiment entries and provide no
accuracy estimate. Actual-interface validation confirmed single-pass static
audits and recovery from injected early prose under the final caps; the test
injection is excluded from production and substantial results.

Exact implemented protocol

1. A candidate-blind auditor receives only the question, bound patient/current
time assumptions and shared semantic guide. It derives requirements with exact
substring quotes and model-supplied spans. For a uniquely occurring exact quote,
the host derives its actual [start,end) position from the original question,
retains the supplied span and records normalization. Repeated/missing quotes
remain invalid even if a model span selects one occurrence. This question-only
normalization precedes solver reveal. The contract is frozen and hashed before any solver code or
resource-selection metadata is revealed. Invalid contract output is recorded and
skips auditing; it does not block the independent primary solver.

2. The primary solver reuses SingleAgent's continuous retrieval/code/debug/final
and one source-feedback correction trajectory. A solver-specific retrieval
dispatcher uses the existing Toolbox validation, patient/time binding, linked
closure and completeness metadata. Starting packets do not establish complete
searches. A persistent scoped dispatcher retains excluded counts and original
records with unknown patient/time binding. It retries those original records
against the unchanged validator after a later retrieval adds source context
(e.g. Condition then linked Encounter). Unresolved scope is an actual source-check
issue, including for zero/false absence answers; it cannot certify completeness.
Historical successful searches are not enough: completeness is recomputed from
current unresolved scope. Unlinked Medication/Location originals are also
deferred: complete HTTP closure does not imply their ownership roots are held.
Later valid roots can recover them with the same validator. Known future-only
roots currently leave shared metadata unresolved rather than proving absence;
this is a conservative false-abstention risk, documented below. This stricter
team-only dispatch is part of the treatment.
The shared SingleAgent class, prompt, tools, field checker, sandbox,
budget accountant, context compactor and scorers remain byte-identical to V2.

3. The solver receives a visible remaining token/tool signal before each actual
model call, plus a request to finalize before inspection consumes its allocation.
Before the first real solver call, a team-only flag requires an explicit final
execution. Early unexecuted JSON/prose receives the unchanged SingleAgent
final-execution feedback and cannot terminate as an outer-gate abstention.
It stops at the boundary after the entire current tool batch when its explicit
validated final artifact matches the workspace. A deterministic host boundary
message replaces the otherwise unnecessary full-context synthesis model call.
The existing automatic source check still executes before acceptance. A later
retrieval, failed non-inspect calculation or denied requested mutation/retrieval
in the same batch invalidates readiness. Inspect diagnostics cannot replace a
final. A first artifact can still implement the wrong question: this lifecycle
change is not an oracle early-stopping claim.

4. The auditor then receives actual final code, its frozen contract, immutable
workspace identity, retrieval ledger and bounded source samples. It receives no
rendered candidate answer. It gets no inspection tools and makes exactly one
static audit completion. The targeted host executor supplies actual replay,
changed-source counterexample and source-check feedback for a supported proposed
repair. PASS/FAIL/UNKNOWN/N/A checks and at most one expression
repair are parsed; vague disapproval, malformed output, unavailable auxiliary
calls and UNKNOWN do not veto a valid primary.

5. A repair is restricted to a unique matching AST expression. This version
supports one numerical operator over explicit valueQuantity.value reads with an
unchanged question-literal threshold, or one measurement ordinal index over an
unambiguously ascending effectiveDateTime-sorted variable. It rejects compound
changes, scalar aliases, uncertain sorts, sorted-variable mutation/aliasing,
AugAssign/deletion/shadowing, item assignments and unsupported concepts/dates/visits/aggregations.
Whole-question multiple supported thresholds or multiple ordinal tokens are
conservatively unsupported: a quote alone cannot bind a clause to an AST node.
The reproduced `<70 OR >70` false-positive replacement is now blocked; its
correct primary is preserved. The first-weight/last-height ambiguity is also
blocked. Additional threshold synonyms/negation and multiple numeric AST
comparisons are conservatively unsupported. These are demonstrated failure
regressions, not merely caveats.
Question spans establish provenance, not semantic truth. Supported literal
operators/ranks are parsed deterministically; broader intent remains uncertain.

6. The host replays the original calculation on the exact frozen workspace,
then runs the patched code in the same existing sandbox. No model rewrites or
new retrieval are allowed in the targeted phase. Ordinal replay captures actual
sorted IDs as diagnostics while reproducing the primary's typed artifact.
Replacement requires a changed answer, nonempty changed contributing-ID set,
unchanged non-Observation dependencies and original-field witnesses drawn from
the changed IDs. Predicate replacement is restricted to a How-many question
with integer answers exactly equal to each artifact's contributing Observation
count; this rejects a compensating len(rows)-1 calculation. Ordinal replacement
requires answers equal to the directly selected original source quantities;
converted or compound ordinal outputs remain unsupported. Each predicate
witness must actually change membership under
the old/new operator. Ordinal witnesses must match the exact old/new source ranks
and have distinct, ordered original effective times. An equal-time tie does not
establish this strict ordinal discrepancy.

7. The replacement undergoes the same final metadata and re-fetched source gates
as the primary, including patient, field/value, current time, question windows,
encounter and unit checks. A source failure, insufficient checker budget,
limitation, missing completeness, stale/irreproducible artifact or unsupported
witness preserves the source-valid primary. Source-valid release records
final_check_issues=[]; failed primary release records the actual source/execution
issues. Targeted candidate failures remain separately in the proof audit.

8. No mandatory third solver or final synthesis call exists in this candidate.
The controller releases the chosen executed artifact unchanged and stores primary,
contract/hash, audit, targeted replay/patch/witness/check, phase accounting,
retrieval ledger and release-policy reason. Standard outer draft/final/revised
fields describe the initial solver draft through the final released result,
covering both source-feedback revisions and targeted changes. Separate
solver_source_revised/targeted_revised flags and primary_revision preserve the
two mechanisms for transition/harm diagnostics. Assurance is source-checked local
constraint correction, never fully independent semantic verification.

Exact fixed caps

Same parent model, provider/base URL and reasoning settings for every role.
Common global ceiling: 200,000 accounted model tokens, 30 executed tool calls.
Existing per-request context guard/compaction and missing-usage failure remain.
Contract phase: 10,000 tokens / 0 tools, one model completion.
Solver phase: 175,000 tokens / 27 tools, at most 20 actual model calls. At most
25 model-requested tools; TWO automatic original-source checks are reserved and
included in the 27. Smaller global budgets also reserve those source slots.
Program-audit phase: 15,000 tokens / 0 tools, exactly one static audit completion.
Both the Role allocation and empty Toolbox deny any requested probe. An auditor
that requests a tool instead of JSON is an auxiliary failure that preserves P.
Targeted phase: 0 model tokens / 3 tools: original replay, patched final, and
replacement source check. All three count in the same global 30.
Totals of phase ceilings: 200,000 tokens / 30 tools. Unused budget stays unused.
Local phase ceilings temporarily cap provider completions; they restore the
global ceiling afterward. Local refusals remain in phase diagnostics without
contaminating later phases; unknown provider usage or reported local/global
ceiling overshoot stays fatal. A provider cannot exceed a phase ceiling and
then spend a later phase's reserve merely because it remains below 200,000.

Scope and tradeoffs

This changes team topology/lifecycle and adds a semantic perspective, while
leaving shared solver/helper/source/scoring code untouched. The early solver
boundary, budget signals, validated retrieval ledger and audit are a combined
treatment. A win cannot be attributed solely to role count or the auditor.

A completed-control aggregate diagnostic reported 289/300 rows with successful
final tool artifacts; the first artifact matched the typed reference in 229.
Seven first matches ended wrong, three first mismatches ended correct, and 39
rows contained multiple finals. The actual control score remains 231/300. This
post-hoc observation has both recovery and lost-self-refinement implications.
The first artifact has not necessarily passed host source gates. The runtime
does not receive this diagnostic, gold values, or per-question routing hints;
it uses the same predetermined batch boundary for every question. This is a
lifecycle hypothesis to evaluate, not a guaranteed accuracy improvement.

Many real queries will receive no automatic semantic repair. Calendar windows,
concept mappings, medication links, joins, counts/distinct/ties and paired
arithmetic are audited but remain UNKNOWN unless the narrow supported rule
applies. The integrated solver must solve those competently. A contract auditor
can still miss a mistake, and a source-valid primary can still be semantically
wrong. Preserving it trades uncertain wrong releases for fewer false vetoes.

The required changed-contributor gate rejects an ordinal fix when both artifacts
correctly preserve every sort input in the same contributor set. Supporting that
case safely needs a separate executed selected-ID lineage field or a constrained
plan executor, not weakening the current contributor gate. This is a material
limit of this conservative insurance implementation. Retained unlinked
metadata can also cause an abstention when all patient references are known
future events: this candidate does not implement an exhaustive root-graph
negative proof. Fixing that needs completed original Request/Admin searches and
source-only reachability, never an auditor claim or a weakened date gate.
A third blind vote remains
an unimplemented separate treatment requiring a new recorded allocation/policy.

Research mechanisms and boundaries

CodeAct's explicit interactive execution feedback supports bounded diagnostics:
https://arxiv.org/html/2402.01030v4
https://github.com/xingyaoww/code-act
CoVe's factored verification motivates deriving intent before candidate reveal:
https://aclanthology.org/2024.findings-acl.212/
Reflect-SQL motivates localized constraint repair instead of whole-program drift:
https://arxiv.org/html/2601.06678v1
BATS/Budget Tracker provides source support for visible remaining budget signals:
https://arxiv.org/html/2511.17006v2
https://github.com/google-research/budget-aware-agent/blob/main/src/agent_budget_tracker.py
Its search sampling, selection models and continuation policies are different;
this implementation does not force continuation until the budget is exhausted.
Independent voting cannot certify correctness of correlated interpretations:
https://arxiv.org/html/2510.17472v1
https://arxiv.org/html/2508.17536v1
Additional research/tradeoffs are in the earlier isolated design_protocol.txt and
research_execution_verification_addendum_20261013.txt. This source candidate does
not import gold templates, SQL, answers, trained reward models or patient exceptions.

The parent chose V3.2 as the final proposed treatment: replace probe-then-synthesis
with one static question-contract/code audit. Keep token ceilings 10k/175k/15k/0,
reallocate tools to 0/27/0/3, and require final execution from the solver's first
turn. The static auditor still sees frozen independent intent, code and bounded
source previews, but cannot verify broader semantics by probing. Actual execution
and original-field witnesses remain in the bounded targeted host phase. This
change is recorded before the substantial run, rather than attributing V3.1's
incomplete audits to a finished semantic verifier. Further protocol changes are
reserved for demonstrated bugs, not post-hoc question-specific routing.
