POST-V6 H1/H2 DESIGN ASSESSMENT — READ ONLY, NO IMPLEMENTATION OR WINNING PREDICTION

Recommendation
H2 is a reasonable next test: preserve the full natural actual Single A, then run a fresh actual Single B using only affordable residual resources, with its own starting packet/retrieval/execution/source feedback and one existing-candidate selector. This addresses both V6's mechanically fragile one-shot B interface and its fixed-evidence restriction, reusing a demonstrated solving policy rather than adding a new program contract. H1 is a narrower engineering alternative and a useful ablation hypothesis, but its own-feedback improvement can increase eligibility while keeping A's retrieval omissions. Neither has demonstrated complementary correctness here. Root has chosen H2 for prospective engineering review; no design is implemented by this assessment. The B+selector treatment is bundled, so a future gain would not isolate retrieval, feedback, or selector prompting as its cause.

H1 versus H2 mechanics
H1 starts blind to A's answer/code/history but intentionally sees A's selected held workspace. It can use real Python/source failures for bounded repairs, which plausibly addresses V6's49 missing-metadata and50 malformed-ID leading failures. A source-clean semantic error may give it no corrective signal; no held-record feedback can recover evidence A never retrieved. Its implementation is smaller (one immutable workspace), but needs a newly specified solver/feedback loop and explicit repair-versus-selection finish budgeting.
H2 creates a clean actual Single B from original question/context/guide with no A answer, code, history, selected types/queries or workspace. Actual Single then creates its OWN deterministic original starting packet; it is not literally empty after setup. Both agents share that packet algorithm, underlying patient store/model and potentially cached responses, so independence is conversational/retrieval-policy separation, not independent data or guaranteed error diversity. B's original tool calls, inspections, final computations and automatic source feedback remain its natural policy under smaller residual caps. Do not force a convenient early final. The ordinary starting-packet fetch occurs outside the counted agent-tool dispatcher in current Single; preserve the common initialization behavior and explicitly record the additional initialization/I/O, rather than claiming no duplicated retrieval work. Cache hits still count each agent tool invocation.

Ownership/fallback and manageable implementation scope
H2 must preserve distinct A and B workspace/program/execution/check identities. Check B against B's held namespace and actual original-source result, never against A's workspace. A selector chooses exactly an existing released A, released bound B, or UNKNOWN; it does not merge evidence, run code, create a third answer or certify semantics. Honest limitations remain visible. Root's proposed question-derived requirements and concrete evidence comparison is a fallible tool-free selector change that must be evaluated as part of the candidate.
A failed/oversized/ineligible B or malformed/UNKNOWN selection preserves the entire released A under known usage. Do not let an auxiliary local budget refusal leak into outer Base normalization and replace A with a synthetic null. A fatal accounting/provider event still makes the whole attempt failed; fallback integrity is not an accuracy floor. Record actual A-only, B eligibility/complementarity, selection harm/help and fatal-stage losses separately, retaining every first attempt.

Reusing Single is straightforward at the policy boundary, but the existing continuous_primary._adopt explicitly requires a clean host and must not simply be called twice. B needs a separate local ledger with its actual snapshot adopted once as a delta into the outer aggregate, plus one explicit selector call. Its workspace must be isolated before any retrieval or Python mutation. Audit persistence needs an explicit versioned representation of both candidate snapshots (or a binding equivalent), with chosen/unchosen ownership retained; existing audit_store supports only trace,retrieved_fhir_resources,revision.messages, so silently stuffing a second workspace into an unbounded inline revision or overwriting A would not suffice. This is bounded controller/ledger/owned-audit/guard work, not a need to change shared Single prompts/tools/source semantics or adopt a new agent framework. No feasibility conclusion waives those implementation tests.
