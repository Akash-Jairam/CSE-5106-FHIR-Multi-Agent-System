Prose and source failures:
- _requires_final_computation starts False and becomes True only after the model requests mode=final. Thus an unmodified Single can legitimately release source-checked prose without any final program, including a None/empty-reference answer. This output remains A but is critic-ineligible. Forcing _requires_final_computation from turn one or asking for an extra final program changes the primary policy; if all primaries must be executable, that is a separately declared change requiring the same treatment in the paired control.
- A successful final artifact controls the candidate when the model finally emits a no-tool reply, even if its prose is malformed/different. However the model can first inspect more, fetch records, run another final, or revise normally. Do not cut this continuation short at the first executed artifact.
- Retrieval (including a failed request actually dispatched) and auto/final calculations invalidate stale authority; inspect preserves it only on the same workspace. A tool rejected before _handle_tool_call because the cap is exhausted does not take this invalidation path in the current Single. A strict observer can mark critic eligibility uncertain in this corner without altering A; fixing it for the primary would be a disclosed shared-policy change.
- Source problems yield the ordinary Single revision opportunity, then an abstention if unresolved. Do not reclassify its withheld computed artifact as released A, do not send it to the critic as a valid primary, and do not add Ledger's global unresolved-metadata veto. Conversely, preserving Single does not certify patient/time completeness for every uncited input: its dispatcher keeps fetched resources, while check_fields verifies cited original fields; this limitation remains explicit.

Budget/call decisions that must be made prospectively:
- Minimal faithful option: 175k/27 INCLUSIVE primary tools and 25k/3 critic, global <=200k/30. Single currently has no 25-model-requested +2-automatic reservation: both explicit check_fields and automatic checks use the same _take_tool_call. Therefore do not advertise a 25+2 guarantee if simply setting max_tool_calls=27. At 27 requested tools the automatic check may be refused exactly as in the natural policy under that cap.
- If 25+2 is mandatory, implement a small new admission shim that distinguishes requested vs automatic calls and disables further requested tools at 25 while keeping two automatic slots. This is a real policy change (and prompts/tool-refusal history can change), even without budget nudges. Preserve natural continuation; do not use Ledger's early boundary or scoped retrieval. It should receive its own paired-ablation label.
- max_iterations=30 means up to 30 real primary model-call attempts; the two automatic source checks are TOOL calls within those iterations, not two extra model turns. Adding <=2 critic calls permits up to32 actual model-call attempts versus the current control's30. Disclose this even though total tokens/tools are equal. If the entire system must share a hard30 model-call ceiling, predeclare primary28+critic2, which preserves loop semantics but changes the primary call allotment; or test a correspondingly declared32-call control. Never silently call30+2 equal to30.
- Role.run is not a substitute for the primary: it starts a different context and may add final-task prompts and an extra synthesis call after max_turns. Use a separately admitted <=2-call critic interface; observed SDK journal sends and controller attempts remain distinct on errors.
