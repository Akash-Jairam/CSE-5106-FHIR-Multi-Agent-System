Generic executable-critic decision memo — proposed next bounded hypothesis
2026-10-15. Primary-paper/official-code research plus completed-run mechanisms only. No inference, source changes or new holdout inspection. This is a recommendation, not a selected/frozen design or claimed improvement.

Recommendation
The strongest bounded next experiment is the unchanged continuous V3 primary, followed by a witness-first executable critic on its frozen workspace. Replace V3's unused blind contract10k and ineffective static audit15k with one25k critic; keep primary175k/27tools and overall200k/30. The critic has at most3tools: one inspect, one replacement final execution, one original-source check. Do not add a planner, duplicate independent full solver, majority vote, mandatory recomputation or benchmark-specific repair grammar. Keep the original valid artifact unless the critic proposes a concrete question-anchored discrepancy with an executable/source witness and its replacement passes every execution/source gate.

This last policy is fallible model-mediated semantic judgment. A generic host can validate source facts and executable lineage, not prove arbitrary natural-language equivalence. If the requirement is a formal guarantee never to harm any correct primary, broad generic repair is not feasible here without trusted specifications/oracles. The experiment must measure harmful revisions, not advertise that guarantee.

Why this mechanism fits the completed evidence
V3d's primary produced232/300; its static audit made0repairs across283 valid audits. V4 produced218 versus fresh Single239 and V3d232, despite0team API errors;25/29 paired losses to Single were source-valid wrong answers. The dominant gaps are semantic, especially temporal selection, with concrete examples involving invented clocks, missing extrema/grouping, wrong projection and reference interpretation. These observations motivate inspecting actual code/intermediates after a primary has worked, rather than supplying another untested interpretation before solving. Plan visibility is associated with many regressions but was widespread, so these data do not isolate causal plan harm. V4 changed exposure, audit removal and allocation together.

Keep V3's primary prompt/input/guide/tools/trajectory,20real model calls,22host slots,175k token ceiling and27tool ceiling (25requested+2automatic checks) unchanged. The removed V3 blind contract was not visible to its primary, so its removal need not change primary information. Frozen primary selection remains its existing first-valid-final lifecycle and original source-feedback revision; do not route per question using any completed score or reference answer.

Exact proposed runtime
A. Require an already source-valid primary with explicit executed artifact, exact workspace/code hash, finished current tool batch, no unresolved scope/source issues, and nonfatal verified accounting. Freeze artifact, original records, workspace, retrieval ledger/completeness facts and original context. A primary that failed this contract is not rescued by a new whole-answer solve in this candidate.
B. First critic call sees original question/context, unchanged public semantic guide, intact executed program and hash, immutable workspace/source handles, and retrieval/completeness ledger. It sees neither the separately rendered answer nor prior operation prose as authoritative evidence. Do not call it answer-independent: code/records may expose selected values. Exclude reference answers/programs, scores, question/template IDs and historical per-case advice. If complete essential code/metadata cannot fit the reserved context, record coverage UNKNOWN and retain primary; do not silently truncate it.
C. First response is KEEP/UNKNOWN, or one focused inspect request tied to a falsifiable mismatch. Host permits only mode=inspect on a deep copy of the frozen workspace; no retrieval, final, field-check tool, batches or hidden extra calls. The one sandbox invocation counts as critic tool1. It may reproduce actual code and expose bounded intermediate facts/source handles; any composite replay is explicit in the audited code. Do not treat a model-written expected answer or pass/fail assertion as a trusted test oracle. Raw source facts can be checked; expected clinical answers cannot be assumed.
D. If the inspect succeeds, a second and final critic call receives its bounded factual result and returns KEEP/UNKNOWN or one patch. No tools on that second call. Require exact original question/context quote, actual code region, concrete observed discrepancy, source-backed witness handles/paths/values, explanation of how the patch addresses that obligation, and explicit other obligations preserved. Use one uniquely anchored bounded old/new code region; disclose that textual locality does not guarantee small semantic effect. Missing/ambiguous provenance, vague concern or uncertainty -> retain primary.
E. Host validates JSON/finite values, exact quote provenance, original code occurrence/hash, original source handles/values and immutable-workspace binding. Tool2 executes the entire patched original program once on a fresh copy in final mode. Accept only the ordinary strict executed artifact; never a critic prose answer. Failed metadata/execution gets no free correction call.
F. Tool3 performs the unchanged original-source checker using original question/patient/current_time and persistent unresolved-scope state. Check raw/global checker errors as well as citation issues; evaluate empty/completeness conditions against the new candidate, not an old primary pointer. No relaxed patient/date/field gate and no artificial null-to-positive preference.
G. Release candidate only if the concrete discrepancy, nontrivial patch effect and all lineage/execution/source checks hold. Record assurance as executed_source_checked_critic_proposal, not verified_semantic_truth. Every nonfatal auxiliary format, known-budget refusal, inspect, patch, execution or source failure preserves the untouched primary. Unknown provider usage or reported overshoot remains globally fatal, including when a valid primary exists. Preserve original, probe, alternate, patch, rejection/release rationale and all charged work.

Why freeze workspace and omit retrieval initially
In the current engine any retrieval invalidates a prior final and can alter scope completeness, even if the retrieval fails. Discovering a newly relevant record then failing to repair makes blind fallback to the old answer unsafe. A copied workspace and independent candidate state make fallback honest. This bounded critic cannot fix missing retrieval; return UNKNOWN for insufficient held evidence. Adding retrieval later is a distinct protocol requiring a revised stale-artifact/completeness policy, not a free capability inside these3slots.

Accounting and interfaces
Critic uses at most2actual model calls, with no Role.run implicit synthesis after a tool, no final free synthesis and no automatic extra sandbox/check.25k includes both repeated inputs, outputs and tool preview. Before call1 reserve the complete second input plus a bounded patch response; long code can exhaust this allowance.0tools for KEEP,1for inconclusive inspect,3for attempted replacement. The host's in-memory hashes/schema/source-path comparisons are not extra external executions. All real sandbox invocations and original-source checks are charged. Keep current native SDK/transport/retries/timeouts and safe journal unchanged.

Use generic CriticCore contracts: TaskContext, ExecutedArtifact, SourceHandle/FieldPath, WorkspaceSnapshot, InspectCapability, Witness, Patch, CandidateResult and ReleaseDecision, serialized as ordinary finite JSON plus declared tools. Existing FHIR patient/time/source/completeness rules are a TaskAdapter, not a new learned or hardcoded question classifier. No question IDs, template IDs, answer-kind shortcuts, literal benchmark dates/concepts or branches for observed failed examples. Generic selection/grouping/order/projection/reference facts can be described by the model; do not turn the observed failure list into runtime repair classes.

A real effect need not change contributing IDs: grouping, unit conversion or output projection can change with the same source records. Conversely changed IDs alone do not prove a repair. Require the witness to identify the actual changed derived behavior, retain full source lineage and explain all downstream effects. Examples for offline red-team tests should cover wrong-clause binding, complementary/compensating arithmetic, missing candidate population, null-before-rank versus rank-before-null, timestamp ties, field fallback/reranking, unit/reference ambiguity and fabricated source values. These test generic safety properties; they must not become per-case gold routes.

Research mechanisms and what does NOT transfer
CRITIC (ICLR2024) grounds critique in tools and passes prior code/execution feedback to revision. Its official program code runs four rounds with two model calls per round, not our3tool budget, and its revisions can damage initially correct answers. Transfer external execution feedback and retained originals, not an oracle-wrong-only route or guaranteed repair claim.
https://arxiv.org/html/2305.11738v4
https://github.com/microsoft/ProphetNet/blob/5cf70eb41cdaa1d8faa3e1265d95ee5792d49a53/CRITIC/src/program/critic.py

Self-Debugging (ICLR2024), AppendixG.5, retains an earlier program if a further revision fails a supplied test. That supports nonfatal fallback and preserving tested properties. Our QA task lacks a trusted full semantic test suite; passing an invented assertion does not inherit the paper's test authority.
https://arxiv.org/pdf/2304.05128v2

Revisiting self-debugging with self-generated tests (ACL2025) finds wrong expected outputs can mislead repair; intermediate execution information can help without making generated expected values the oracle. Transfer factual trace inspection rather than a model-generated answer key.
https://aclanthology.org/2025.acl-long.881.pdf

SQLDriller (SIGMOD2025) generates small counterexample tables and asks an NL oracle to distinguish queries, retaining originals without counterexamples. Its reported remaining harmful revisions expose the crucial limit: a data counterexample shows two programs differ, but a fallible NL oracle still decides which is intended. ParSEval explicitly distinguishes disproof by execution from bounded agreement evidence, with UNKNOWN for unsupported cases. Neither can certify our arbitrary Python/FHIR program without a trusted query/specification.
https://ipads.se.sjtu.edu.cn/zh/publications/SQLDriller.pdf
https://github.com/SJTU-IPADS/SQLDriller/blob/651401923af77db68f7f32b060f57da1b8e1e444/dataset_refine.py
https://github.com/sfu-db/ParSEval/blob/88cfe245bcf249a5b0df561a6b09c116ff2a2896/README.md

LLM-CEGIS-Repair (AAAI2025) localizes edits using counterexamples from a supplied test suite and may include a reference program. Its repository warns current code is not the paper reproduction. COVER (2026) uses stable constraint nodes/local repair but its main verifier has a reference-model oracle. These motivate bounded location/trace interfaces; their oracle-backed rates do not substantiate our semantic release gate.
https://github.com/pmorvalho/LLM-CEGIS-Repair/blob/7fe749b16a7a1367f2a519492a5d8689af06a896/repair.py
https://journals.sagepub.com/doi/10.3233/FAIA260737

CHESS's official SQL revision path treats empty results as an error cue, and its unit tests are LLM judgments rather than executed truth specifications. CHASE-SQL spends many candidates and uses a trained selector. SHARE trains specialized assistants and identity examples to reduce overcorrection. These are not evidence that another same-model critique prompt automatically wins under equal200k/30. Do not force nonempty answers, borrow their uncounted ensembles, or import benchmark answer supervision.
